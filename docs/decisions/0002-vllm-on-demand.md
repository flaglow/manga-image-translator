# vLLM 로컬 LLM 온디맨드 운영 결정

## 배경

같은 물리 GPU(RTX 4090)를 번역 파이프라인뿐 아니라 다른 프로젝트(ML 학습 등)가
공유한다. vLLM 소형(hymt2-small, ≈4.8GB VRAM)을 상시 상주시키면 번역 수요가 없는
시간에도 GPU를 점유해 다른 프로젝트를 방해했다(2026-10-30 실제 사고 — 학습 작업
실행을 막아 사용자가 즉시 철거를 지시). GUI의 기존 셀프힐(죽으면 무조건 복구)과
docker `unless-stopped` 정책이 무단 부활 경로로 작동해 문제를 악화했다.

## 검토한 대안

| 대안 | 판정 | 근거 |
|---|---|---|
| 상시 상주 + 셀프힐 (기존) | **기각** | 무수요 시에도 GPU 점유 — 다른 프로젝트 방해 사고 |
| 즉시 기동/즉시 정지 (0초 유지) | 기각 | vLLM 시작 ~1분 — 작업마다 지연·마찰 |
| **온디맨드 (채택)** | **채택** | 수요 시 기동 + 무수요 3분 후 정지. 시작 지연은 finish 워커·augment 러너의 헬스 대기로 흡수 |

## 결정

**결론: vLLM(hymt2-small)은 온디맨드로 운영한다 — 큐에 작업이 있을 때만 GUI 스케일러가
기동하고, 무수요 3분 후 자동 정지한다. 재시작 정책은 `no`로 유일한 기동 경로를 GUI로 일원화한다.**

## 결과와 후속

- 구현(`translate_gui.py` `_vllm_demand`, 20초 틱): 작업 유무 판정 → 기동/정지,
  finish 워커·augment_runner는 헬스 대기(최대 5분) 후 컨테이너 실행. GLM 계열
  작업은 대기 없이 통과.
- `hymt2` 브리지 네트워크는 상시 존재(빈 브리지 무비용) — 컨테이너 attach 일관성.
- `restart: "no"` (compose + `docker update`) — docker 데몬 재시작·정책 재활성화로
  무단 부활하는 경로 차단.
- startup.sh은 컨테이너를 띄우지 않는다(네트워크 보장만).
- 되돌리는 조건: 시작 지연(~1분)이 운영상 감당 불가한 정기적 증거가 쌓일 때
  상시 상주 또는 하이브리드(예열 시간대) 재검토.
