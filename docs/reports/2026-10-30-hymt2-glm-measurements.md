# Hy-MT2 로컬 LLM 파이프라인 측정 보고서 — 2026-10-30

아키텍처·설계 근거는 `docs/guides/hymt2-pipeline-design.md`(이하 설계문서).
본 문서는 당일 실측 전체 기록이다. 모든 품질 지표의 레퍼런스는 **프로덕션 GLM 로그
다수역**(코퍼스 585K 쌍)이고, 정확일치는 동일 문장 요구(보수적), 바이그램 F1은
부분 일치 반영(관용 변형 반영)이다.

## 1. 품질 — 계층별 평가 (샘플 700, GLM 다수역 기준)

계층: A=TM키(share≥0.75·빈도≥3) 150 / B=벡터DB 비TM 350 / C=GLM불일관(share<0.5) 200

| 지표 | 1.8B 단독 | 7B 단독 | 1.8B+게이트(v3) | GLM(현행) |
|---|---|---|---|---|
| TM키층(A) 일치 | 97.3% | 97.3% | 97.3% | — |
| B층 정확일치 / F1 / F1≥0.6 | 8.0% / 39.6 / 24.5% | **10.6% / 47.0 / 35.0%** | 7.4% / 39.5 / 23.8% | 자기일관성 31% |
| C층 정확일치 / F1 / F1≥0.6 | 4.5% / 34.7 / 25.6% | 5.8% / 36.5 / 27.9% | 5.5% / 35.2 / 26.1% | — |
| 페이지(25세그) 지연 | 2.4s | 3.4s | ~2.6s+수리 | **12.2s** |
| API 토큰/세그 | 0 | 0 | 0 | ~85 |

- 계층별 근거: 참조주입(벡터 근접 예시)이 양 모델에서 **F1 +6~12pp** — 참조가 품질
  핵심 레버. 7B의 우위는 B층 무참조(+8.6pp)에 집중, C층 무참조는 역전 → 무조건
  7B 직행은 금지(옵션화).
- 스타일 지시(Hy-MT2 공식 【...】 형식, 반말 대사체)로 1.8B의 해요체 계통 편차 교정
  (예: `どうかな？` 부디 어떠신가요?→어떻게 생각해?). 정확일치율 변화 미미.
- **GLM 자기일관성 31%가 동일 지표의 실용 천장** — "GLM과 다른 문장 ≠ 오역".

## 2. 품질 — 동일 문장 3자 비교

### 무작위 코퍼스 42문장 (비TM, share≥0.5)

1.8B F1 56.9 / 7B F1 67.9 / 7B 우세 17·무 17·열세 8.
7B 강점: 고유명사(`七瀬瑞穂→나나세 미즈호`, 1.8B `나세 마이후` 오역), 어휘 뉘앙스
(`偏った→편향된` vs `이상한`), 공지·안내 장문(F1 0.78 vs 0.66).

### 실제 대사 페이지 60문장 (최근 작업 폴더, 백페이지 상용구 제외)

**1.8B F1 40.2 / 7B F1 52.3 / 7B 우세 38·열세 13** — 감정 실린 대사에서 7B 우위
더 큼. 대표: `挿入れちゃダメッ‼` 7B 정확 일치(1.8B `넣지 마!!`), `もっと…` 7B `더...`
일치. 세 모델 제각각인 유효 케이스도 다수(`なにこれっ` 3개 전부 통용).

→ 근거로 **앵커이탈 게이트 임계 0.3→0.45 상향** (7B 비중 확대). 게이트 상향 25건
짝 비교: 개선 9 / 동일 12 / 악화 4 (`知るかよ` F1 0→0.91).

## 3. 파일럿 — hd-pilot 14페이지, 배타 흐름 전체 (설계문서 §8)

렌더 18.6s(1.8B 단독) → 스플 13 → 수리 스왑 12건 → 재렌더(캐시 히트) → 잔여 2차
수리 → **빈칸 0·스필 0 수렴**. 티어 분포: 1.8B 78%(참조주입 18%) · TM 14% · 7B 수리
7% — ≤1.8B+TM 해결률 ~93%. 결함 2건 발견·수정(페이지 병렬 `_stat` 레이스, 중첩
bind-mount root tmp).

## 4. 처리량·자원 — 컨테이너 스케일링 (Pass A 전처리)

| 구성 | 처리량 | VRAM | VRAM 효율 |
|---|---|---|---|
| GPU 1컨테이너 | 22.5 p/분 | 5.2GB | **4.3 p/분/GB** |
| GPU 3컨테이너 | 34.5 p/분 | 15.6GB | 2.2 p/분/GB |

3배 증설 → +53% (컨테이너당 효율 49%↓) — GPU 경합 확정. vLLM(4.8GB) 상시 운용
예산에서 4컨테이너는 물리적 불가(≈25.6GB>24GB). **소수 정예(1~3)가 최적**.

## 5. GPU 저활용 분석 (util 0~7% 구간 다수의 원인)

- 병목은 GPU 아닌 **단계별 GPU↔CPU 직렬 구조**: pre 페이지당 GPU(검출/OCR/inpaint)
  ↔ CPU(마스크·PIL) 왕복 — CPU 버스트 1,030%(10코어), 호스트 전체 여유(24코어 load ~4).
- vLLM 동시요청 실측 **0~3개**(10분) — 배치 크기 문제가 아니라 공급 부족(번역은
  짧은 버스트, 렌더 CPU가 더 김). finish 비병목 → vLLM 저활용은 건강 신호.
- 대응: `FINISH_CONCURRENCY` 적응형(로컬 LLM 10 / GLM 3 — GLM 429 한계와 분리).
  10레인 효과 실측은 차후 배치 예정.

## 6. 실배치 운영 실적 (21권+ ~1,990p, GPU 1컨테이너, ~40분)

- pre 22.5 p/분 + finish 3레인 체이닝 병렬 — 전 구간 무중단, API 비용 0.
- 스플 503건 → 7B 수리 492건 → **수리 캐시 544세그먼트** 자산화.
  잔여 11건은 OCR 쓰레기(`ER♡`, `gpt64` 등) — 번역 불가 정상 거부.
- 운영 순서 권장: **큐 소진 → `./hymt2_repair.sh` → 수거** (수리 전 수거 시
  스플 구간 빈 칸으로 렌더 — 수리본은 캐시 보존).

## 7. 종합 결론

- **속도·비용**: GLM 대비 3.6~5배, API 토큰 0 — 목표 달성.
- **품질**: TM층은 GLM 동일(재사용). 비TM층은 7B가 유의미하게 근접(F1 +11~12pp)하나
  GLM 관례와의 완전 일치는 아님 — 게이트 임계·7B 비중으로 품질/원가 딜 조정 가능.
  최종 검수(인간 리뷰) 병행 권장.
- **자원**: 단일 4090에서 전처리 1~3컨테이너 + vLLM 소형 상시 + 7B 스왑 수리가
  예산 최적. 스프릴/캐시 순환이 로컬 LLM 단점(단일 모델)을 구조적으로 보완.
